`platform/webhook` runs [webhookd](https://github.com/ncarlier/webhookd) v1.22.1 with one patch (`images/webhookd`): its request log
shows secret query values only as `ok` / `wrong` (so the status code never reaches a log viewer, while guessing still
shows up) and takes the client IP from `CF-Connecting-IP` (the left-most `X-Forwarded-For` can be forged):
each endpoint is a shell script in `platform/webhook/hooks/`, mounted from the ConfigMap `webhook-hooks` (`sites.yaml`
`configmaps:`, built by `node.sh deploy webhook`). It answers at `https://status.<your-domain>`. Every endpoint is a plain 200/500, so any uptime
checker, cron job or phone widget can poll it.

## Access: say nothing to strangers

| Request | Needs | Otherwise |
|---|---|---|
| any `GET` | `?code=<STATUS_CODE>` | a **bare 500**, whatever the real state |
| `GET`/`HEAD /up` | nothing | **200 or 500, no details**: for outside uptime monitors that must not know the code |
| any `POST` | header `X-Token: <WEBHOOK_TOKEN>` and `Content-Type: application/json` | 500, nothing stored |

So nothing about the server leaks, and a missing code can't look healthy. `/up` is the one exception, on purpose: it
runs no checks (it reads the last `/overall` verdict, which the probe refreshes every 30 s, and is 200 only if that was
green and under 5 minutes old), so it's cheap for anyone to call and reveals nothing but up or down. Answers are `text/plain` (readable in a
browser). A Traefik rate limit keyed on `CF-Connecting-IP` (60/min average, burst 100) stops anyone guessing the
code; the normal load from the second machine (watchdog 1/min, autopilot heartbeat 4/min, transcript uploads in
bursts) fits well under it. Both secrets are generated by `anvil-secrets`, never typed, and live in `anvil.env`.

## The endpoints

| Endpoint | 200 means | Notes |
|---|---|---|
| `/space` | the node's root disk has ≥ 10 GB free | body says how much is free |
| `/database` | right now the shared MariaDB accepts a connection and greets as MariaDB, **and** health-watch's last real login + query (as the login-only `health` user, every 15 min) worked and is < 45 min old | 500 with a short reason |
| `/backups` | every CronJob labelled `app.kubernetes.io/component=backup` succeeded in the last 26 h | reported by health-watch; 500 if that report is > 45 min old |
| `/cluster` | per Prometheus: every probed URL answers, every Deployment/StatefulSet is fully ready, no pod stuck unable to start | wrong for 5 min; ignores 10-min work in progress like the rules; `&strict=1` ignores nothing; 500 also when Prometheus can't be asked |
| `/overall` | `/space`, `/database`, `/backups` and `/cluster` are all 200 | lists each result, problems first; Prometheus probes it (`ServerHealthRed`) |
| `/watchdog` | always 200 with JSON `{"ok", "reason", "mutedUntil"}` | for the off-box watchdog: `ok:false` when the Alertmanager heartbeat is > 2 h old |
| `/am_heartbeat` | (POST) Alertmanager's always-firing `Watchdog` alert | every 15 min |

<Aside type="tip">
Point your own phone's status widget or a cron job at `/overall` (and `/error_arduino`): green means everything the
server knows about is fine.
</Aside>

## `/error_arduino`

The **error latch** (the name is historical; anvil keeps it so the two repos stay in sync). **200 `ok`** = nothing
logged; **500** = something errored since it was last cleared. With the code, the body lists the errors, one short
line each. It stays red until you clear it by hand (`platform/webhook/clear-error-arduino.sh` prints the list, then
empties it), so a problem that came and went at 4 a.m. is still visible at breakfast. That's why it is **not** part of
`/overall`, which is the live state.

Who posts there:

- **`webhook/health-watch`** (CronJob every 15 min; cluster-wide read-only `list` on pods and jobs): pods that can't
  start or keep crashing (CrashLoopBackOff, ImagePullBackOff, config errors), pods unready for over 10 min, failed
  Jobs (one line per job per day). It never posts a line that's already there. It also reports to `/database`
  (a real login as `health`) and `/backups` (the backup CronJobs, found by label). Its RBAC: `list` on pods, jobs and
  CronJobs, nothing else.
- The nightly backups, the morning `backup-watch` and the home machine's backup pull.

Keep lines short: the latch is the alarm, the details are in `kubectl logs`.

## Autopilot endpoints

The [autopilot](/components/autopilot/) talks only to this service (the server never connects to the Mac). The
contract is in the autopilot repo's `INTERFACES.md`; in short:

| Endpoint | Who | What |
|---|---|---|
| `POST /autopilot_state` | autopilot, every 15 s | its state (`idle`, `running`, `gave_up`, `paused`), runs today/total, current incident, last run. The response carries queued owner commands. State changes are forwarded to twilio-alert (hold calls while running; summary afterwards). |
| `GET /autopilot` | you, in a browser | status page with links to the commands below |
| `GET /autopilot_reset`, `/autopilot_pause?minutes=N` (10–120), `/autopilot_resume` | you | queue a command for the next heartbeat |
| `GET /autopilot_metrics` | Prometheus | `autopilot_last_heartbeat_seconds`, `autopilot_state{state}`, runs, last result (drives `MacOffline`) |
| `POST /autopilot_run` | autopilot | uploads a run's **scrubbed** transcript in parts; kept 90 days |
| `GET /autopilot_runs` | you | the runs, newest first; `&id=<run>` opens a whole session (served by a small `webhook-files` static server) |
| `POST /postmortem` | autopilot, you, Claude | appends a dated entry to the post-mortem log (a "day" ends at 08:00 local time) |
| `GET /changelog?days=N` | you, the autopilot's prompt | the post-mortems, newest first (`&format=files` to mirror them into git) |

After changing a hook: `scripts/node.sh deploy webhook`. It restarts the pod itself so webhookd sees the new files.
